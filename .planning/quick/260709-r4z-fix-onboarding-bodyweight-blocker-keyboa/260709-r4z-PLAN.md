<objective>
Fix the Phase-3 UAT test-7 blocker on onboarding numeric steps (user report: numeric
keyboard covers the Continue button with no way to dismiss it, and bodyweight is kg-only
for lb users).

Two defects, two independent fixes:
1. Keyboard traps the user — fixed centrally in `WizardStep` (shared by all numeric steps:
   bodyweight, threshold-hr, threshold-pace) via a KeyboardAvoidingView that lifts the
   Continue button above the keyboard, plus tap-outside-to-dismiss.
2. kg-only bodyweight entry — the units step is asked AFTER bodyweight. Fixed by moving the
   units step BEFORE bodyweight in the wizard order (least-invasive; `bodyweight.tsx` already
   fully supports imperial entry and canonical-kg storage per D-05, it just never had `units`
   set yet).

Purpose: Unblock onboarding — currently a user physically cannot complete the wizard.
Output: A keyboard-safe WizardStep and a reordered wizard (sex → units → bodyweight → …).

Out of scope (verified, no change needed):
- threshold-pace unit handling — it already reads `draft.units` and sits after the units step,
  so it is already aligned to the chosen units.
- session logger SetRow keyboard behavior — it does NOT render through WizardStep (separate
  layout), so it is not trivially shared; scoped out per task description.
- "UI is blue" cosmetic — already resolved; `Colors.accent` is volt `#C6F23D` after the
  260709-qmv restyle.
</objective>

<task type="auto">
  <name>Task 1: Make WizardStep keyboard-safe (lift Continue button + tap-to-dismiss)</name>
  <files>apps/mobile/components/onboarding/WizardStep.tsx</files>
  <action>
    The numeric steps use `decimal-pad`/`number-pad` keyboards, which have NO return/Done
    key on iOS, and the Continue button is pinned to the bottom safe area where the keyboard
    covers it — so the user gets trapped. Fix this once, centrally, in WizardStep (it is the
    shared chrome for bodyweight, threshold-hr, and threshold-pace).

    Add two escape routes:

    (a) Lift the Continue button above the keyboard. Import `KeyboardAvoidingView`,
    `Platform`, and `Keyboard` from `react-native`. Wrap BOTH the existing content `container`
    View AND the pinned Continue `Pressable` inside a single `KeyboardAvoidingView` with
    `style` flex:1, `behavior` set to `'padding'` on iOS and `undefined` on Android
    (use `Platform.OS === 'ios' ? 'padding' : undefined`). The button MUST be inside the
    KeyboardAvoidingView (currently it is a sibling of the container under SafeAreaView) so
    that padding lifts it above the keyboard. Keep the SafeAreaView as the outermost element
    with its existing `edges={['top', 'bottom']}` and background.

    (b) Tap-outside-to-dismiss. Wrap the content region (the `container` View that holds the
    question, content slot, and progress dots — NOT the Continue button) in a `Pressable`
    whose `onPress` calls `Keyboard.dismiss`. Give the Pressable `style` flex:1 and set
    `accessible={false}` so it does not add a spurious a11y node. Tapping empty space
    dismisses the keyboard; tapping a TextInput still focuses it (child wins the touch);
    tapping the Continue button still fires onNext (it is outside this Pressable).

    Do not change the visual layout, tokens, progress-dot logic, button labels, or the
    disabled/pressed styling. This is a structural wrapper change only — all existing styles
    from the `styles` StyleSheet stay as-is.
  </action>
