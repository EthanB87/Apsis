# Phase 06 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note (read first):** ROADMAP.md marks this phase `UI hint: no` — "submission logistics;
no new app screens." This is correct: REL-01..REL-04 add **zero new React Native screens or
components**. The app's existing visual contract (`DESIGN-SYSTEM.md`, `apps/mobile/constants/
theme.ts`, `apps/mobile/constants/Colors.ts`) is frozen and unchanged by this phase — no token,
color, spacing, or typography edits are in scope here. What this phase DOES have a real,
prescriptive design surface for for is **store-facing and off-device artifacts** that must look
like they belong to the same brand: the app icon (bug fix, not redesign), App Store screenshots
(framing + captions), and two new static web pages (privacy policy, support). This document
scopes the contract to exactly those three deliverables plus the copy this phase produces
(store listing strings, review notes tone). Everything else below is either "reuse verbatim"
or "not applicable."

## Design System

| Property | Value |
|----------|-------|
| Tool | none — React Native app (unchanged); privacy/support pages are static HTML, no component library |
| Preset | not applicable — shadcn/web registries do not apply to this project (Expo/React Native), consistent with Phase 03/04 UI-SPECs |
| Component library | none for the app (plain RN components, unchanged); plain semantic HTML for the two static pages — no CSS framework needed for two single-column text pages |
| Icon library | not applicable this phase — no new in-app icons; the App Store app icon itself is a static PNG asset, not an icon-font glyph |
| Font | App: unchanged (`Archivo`/`Archivo Expanded` stand-ins + `JetBrains Mono`, already loaded via `expo-google-fonts`, no new weights). Static pages: system font stack (`-apple-system, 'Segoe UI', Roboto, sans-serif`) is sufficient — these are legal/support text pages where load-time and universal readability outrank brand-matching web-font loading; see Typography below for the one exception (page headings). |

**Why no shadcn gate:** This is the same Expo/React Native monorepo as Phases 03–05 (no
`components.json`, no Tailwind/Next.js target) — the shadcn initialization gate is not
applicable, and the two new static pages (privacy/support) are simple enough (single column of
text, no interactive components) that pulling in a component library for them would be scope
creep against the July 25 deadline.

## Typography

**App:** Unchanged — zero new typography roles this phase. `apps/mobile/constants/theme.ts`
`Typography` (body/label/heading/display/displayXl/title) and the Mono/Kicker roles established
in `03-UI-SPEC.md`/`04-UI-SPEC.md` are the complete, frozen set.

**Static pages (privacy/support) — new, minimal contract:**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.6 |
| Label (metadata: "Last updated" date) | 13px | 400 (regular) | 1.4 |
| Heading (page title: "Privacy Policy" / "Support") | 28px | 700 (bold) | 1.2 |
| Section heading (H2s within the page) | 20px | 600 (semibold) | 1.3 |

Rationale: exactly 4 sizes / 2 weights (400 regular for body/label, 600–700 for headings —
counted as the "2 weights" the contract requires: one body weight, one heading weight),
matching the design-contract discipline used elsewhere in this project even though these pages
sit outside the RN app's font-loading pipeline. Do not import `Archivo`/`JetBrains Mono` web
fonts for these two pages — no brand-matching benefit justifies the extra network request on a
page a user visits once, possibly from an App Store review link.

## Color

**App:** Unchanged — no new screens, no new color usage. `apps/mobile/constants/Colors.ts` is
untouched by this phase.

**Static pages (privacy/support) — new, dark-themed to match brand recognition on a click-through
from the App Store listing or in-app link:**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0C0E` (void) | Page background — same void as the app, so a user clicking "Privacy Policy" from Settings or the App Store listing lands somewhere visually continuous with the app |
| Secondary (30%) | `#15171A` (carbon) | Not heavily used on a single-column text page; reserved for any callout/box (e.g. a "data we collect" summary table row background), if the executor adds one |
| Accent (10%) | `#C6F23D` (volt) | Reserved for exactly: link color (in-page anchor links, mailto link on the support page) and the page's top hairline/underline beneath the H1 title — nothing else. No buttons, no CTAs on either page. |
| Destructive | `#FF5A1F` (molten) | Not applicable — no destructive actions exist on either static page |

Accent reserved for: link text color and the single decorative title underline on both the
privacy and support pages — nothing else. Body text is bone (`#F2F1EC`) on void, secondary text
(dates, footnotes) is ash (`#8A9098`) — same roles as the app, reused for visual continuity.

## Store & Static-Asset Specifications

Concrete, executor-ready specs for the three visual deliverables this phase actually produces.

### 1. App icon (REL-01, fixes a verified defect)

- **Source file:** `apps/mobile/assets/images/icon.png` — currently 1024×1024 RGBA (PNG
  colorType 6, has an alpha channel per `06-RESEARCH.md` Pitfall 1). This is a **bug fix**, not
  a redesign: keep the existing plate-mark artwork/branding exactly as-is.
- **Fix:** Flatten onto its final solid background (`#0B0C0E` void, matching the app's own
  background and the existing `android-icon-background.png`) and re-export as opaque RGB, zero
  alpha channel. 1024×1024px, 8-bit depth, no transparency anywhere in the file.
- **Verification:** Re-check the fixed file's PNG IHDR colorType directly (colorType 0 or 2 =
  no alpha; colorType 4 or 6 = has alpha, fails) before every EAS production build that touches
  the icon — do not rely on a visual/eyeball check (an opaque-looking image can still carry an
  unused alpha channel).
- **Do not** redesign, recolor, or resize the mark — this is strictly the alpha-channel defect
  fix per the verified research finding.

### 2. App Store screenshots (REL-01)

- **Device class:** 6.9" iPhone only (D-09) — no iPad, no other iPhone size class. App Store
  Connect scales this set down automatically for smaller devices.
- **Pixel dimensions:** Spot-check the exact current 6.9"-class pixel dimensions against
  Apple's live screenshot-specifications help page immediately before export (research flagged
  this as MEDIUM confidence, cross-checked across secondary sources only — do not trust a
  cached number).
- **Background:** Brand-dark void (`#0B0C0E`) behind every device frame — consistent across
  all captures, no per-screenshot background variation.
- **Screen order (locked, D-09):**
  1. TODAY hero — volt HSS ring + readiness light, caption "ONE NUMBER FOR ALL TRAINING STRESS"
  2. Lift logger ledger — active set-logging screen, caption "LOG A LIFT AT STRONG SPEED"
  3. Run form + History — either two captures or one composited pair, caption "RUN, LIFT, ONE LEDGER"
  4. Apple Health integration — the onboarding connect step OR Settings' "Apple Health" section
     with the connected state + APPLE HEALTH chip visible, caption "YOUR HEALTH DATA, ALREADY THERE"
- **Caption style:** Mono, uppercase, ≤6 words, matching the app's own `Mono` typography role
  (JetBrains Mono 500, wide tracking) — captions are overlaid text, not device-frame chrome;
  keep them short enough to read at thumbnail size in App Store search results.
- **Device state at capture time:** Use realistic-looking but not-real data (no test/lorem
  placeholder values visible) — e.g. a populated 28-day trend, a completed lift session with
  real-looking exercise names, not "Exercise 1"/"Test User."
- **Production tooling:** Simulator captures + device-frame compositing pipeline is Claude's
  discretion (per CONTEXT.md) — any standard device-frame tool (e.g. Fastlane frameit,
  a Figma template, or a manual composite) is acceptable as long as the output matches the
  dimension/background/caption spec above.

### 3. Privacy policy + Support static pages (REL-02, Pitfall 5)

- **Both pages share one minimal layout:** single-column, `#0B0C0E` (void) background,
  max-width 640px centered, `#F2F1EC` (bone) body text, `#8A9098` (ash) secondary/metadata
  text, `#C6F23D` (volt) links only. See Typography above for exact sizes.
- **Hosting (D-04, Claude's discretion on mechanics):** `apsistraining.com/privacy` and
  `apsistraining.com/support` — same static-hosting mechanism for both (e.g. GitHub Pages with
  a custom domain, per `06-RESEARCH.md`'s recommended default), served over HTTPS (hard
  requirement — App Store Connect validates the privacy policy URL is reachable over HTTPS).
- **Privacy policy content owner:** Claude drafts (D-05), tailored to Apsis's actual data
  posture (offline-first; HealthKit read/write stays on-device; only off-device data is Sentry
  crash diagnostics — no PII, no health values, per the D-03 allowlist). User reviews before
  the page goes live — do not treat the draft as final without that review step.
- **Support page:** New deliverable this phase (Pitfall 5 — mandatory App Store Connect field,
  not previously scoped in CONTEXT.md's decisions). Minimum viable: short paragraph + a real
  contact method (a monitored email address as a `mailto:` link, styled as volt text). A full
  FAQ/help-center is explicitly out of scope — this only needs to satisfy ASC's "Support URL"
  requirement with a genuine, working contact path.
- **No interactive components, no forms, no JS required** on either page — plain semantic HTML
  (`h1`/`h2`/`p`/`a`) is sufficient and reduces both build risk and maintenance surface inside
  a 4-week deadline.
